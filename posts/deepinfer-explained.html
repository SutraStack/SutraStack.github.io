01 Start here

DeepInfer is the program DeepSeek runs on its own GPUs to answer your prompts. In October 2026 they opened the source. This page is everything in that repository, the blogs around it, and every acronym it drops — explained from zero.

In one paragraph A trained AI model is just a huge pile of numbers. It cannot do anything by itself. Something has to load those numbers onto chips, take your text, feed it through the numbers, pick the next word, and do that for thousands of users at once without wasting a cent of electricity. That "something" is an inference engine. DeepInfer is DeepSeek's inference engine for their DeepSeek-V4.1-Flash model. It is the thing that makes the model fast and cheap, not the thing that makes it smart.

02 The mental model

Almost every optimization in DeepInfer exists because of one fact: generating text has two completely different phases with opposite bottlenecks. Learn that, and the rest of the repo explains itself.

Prefill vs. Decode

When you send a prompt, the engine does two different jobs:

Analogy Prefill is a student reading a 300-page case file and taking notes — slow, heavy, but they can read many pages in parallel. Decode is the same student then writing the answer one word at a time, re-checking all the notes before each word. Reading is throughput work; writing is latency work. The entire engineering effort is: make the reading cheap, keep the notes small, and never let the writer sit idle.

03 Architecture

Two architectures matter: the production service DeepSeek actually runs (most of which is not in the repo), and the engine that is in the repo. Here is both.

3.1 — The production system (DeepSeek's own deployment)

This is the picture in doc/images/architecture_overview.png, redrawn. Requests arrive as JSON, get turned into tokens, and are routed through three independently-scaled pools of GPUs.

Why split the pools?

Prefill wants few, fat, compute-dense GPUs. Decode wants many GPUs to spread MoE experts. Separating them lets you scale and tune TTFT and TBT independently — at the cost of shipping the KV cache between them.

Why a separate storage cluster?

So any prefill machine can hit any prefix. Local caching would force routing by prefix affinity, which fights the load balancer. Storage also scales — and fails — independently of compute.

Smallest sensible unit

1 prefill + 1 decode engine technically works. In practice the P:D GPU ratio is ~1:1 and decode wants EP64+, so the smallest efficient deployment is about 64 prefill + 64 decode GPUs.

3.2 — The engine (what you actually get)

Inside one engine instance, this is the flow. Note the split brain: Python owns orchestration and the model; a compiled C++ extension (deepinfer._C) owns the hot per-request bookkeeping.

3.3 — Why a C++ core at all?

In decode, a step can take ~5 ms and involve 60+ sequences. If the Python interpreter spends 3 ms deciding what to run, you have lost half your machine. So everything that is per-request, per-step moved into C++: the scheduler, the block allocator, sequence state, the sampler-input packing, and the output objects (which are pooled, not allocated). Python keeps the parts that run once per step or are inherently PyTorch.

05 What happens to one request

The twelve hops

The loop, in real code

deepinfer/engine/llm_engine.py — LLMEngine.step() (condensed)
def step(self) -> np.ndarray[np.uint64]:
    with cpu_timer.record("schedule"):
        # 1. C++ decides this step's batch. Also frees finished sequences.
        seq_metadata_list, scheduler_outputs = self.scheduler.schedule(self.sequence_metadata_pool)

        # 2. Forked sequences need their KV state cloned before they diverge
        if clone_states.size > 0 or clone_blocks.size > 0:
            to_release = self._run_workers("clone_and_zero_states_and_blocks_on_default_stream", ...)
            self.deferred_release.collect_clone_unpins(*to_release)

        # 3. On the last prefill chunk, arm the structured-output grammar matcher
        if scheduler_outputs.prompt_run:
            for seq, md in zip(scheduler_outputs.scheduled_seqs, seq_metadata_list, strict=True):
                if md.is_last_prompt_chunk and md.sampling_params.so_args is not None:
                    md.so_status = 1

    # 4. Pull any finished image preprocessing from the multimodal worker pool
    if self.multi_modal_processor is not None:
        self.multi_modal_processor.fetch()

    # 5. Launch the GPU work. Returns last step's outputs under async scheduling.
    request_outputs = self._execute_model_async_step(seq_metadata_list, scheduler_outputs)
    self.generate_step += 1
    return request_outputs

And the worker side — this is the heart of the zero-overhead design, where the previous step's CPU work is sandwiched between this step's GPU launches:

deepinfer/worker/worker.py — Worker.execute_model_step() (condensed)
# 1. Launch this step's forward (non-blocking — just queues kernels)
main_model_output = self.model_runner.execute_main_model(
    seq_metadata_list, self.gpu_cache, metadata_zos=metadata_zos, total_q=total_q)

# 2. While the GPU chews on that, do the PREVIOUS step's CPU post-processing
request_outputs = self._post_process_step(self.prev_step_state)

# 3. Launch this step's sampling (also non-blocking)
sampler_output = self.model_runner.execute_sample(
    seq_metadata_list, input_metadata, model_output, self.gpu_cache)

sample_end_evt = torch.cuda.Event(enable_timing=True); sample_end_evt.record()
curr_step_state = WorkerStepState(..., sample_end_evt=sample_end_evt)

# 4. Prefill steps post-process immediately; ZOS decode steps defer to next step
if is_prompt or not envs.DEEPINFER_ZERO_OVERHEAD_SCHEDULING:
    request_outputs = np.concatenate([request_outputs, self._post_process_step(curr_step_state)])
    self.prev_step_state = None
else:
    self.prev_step_state = curr_step_state   # ← the whole trick
The consequence Because the CPU is always one step behind the GPU, the CPU does not yet know how many draft tokens were accepted when it schedules step N+1. DeepInfer solves this by having the CPU fix only the total token budget, and letting a GPU kernel (schedule_mtp_varlen.py) redistribute that budget across sequences using the confidence scores that are already on the device. Elegant, and the reason compute_seqlens_k_zos and gather_input_ids_zos exist.

A guard that tells you how serious they are

Any accidental CPU↔GPU synchronisation inside the forward pass would stall the pipeline and silently cost ~30% of throughput. So the forward and sampling launches are wrapped in a context manager that raises if torch detects a sync:

    cuda_timer.record("device_forward", scale=1),
    forbid_cuda_sync(),          # ← raises on any blocking copy / synchronize()

    if run_cuda_graph:
        model_output = self.cuda_graph_runner.replay(cuda_graph_used)

Vendored kernel libraries (the vendor/ submodules)

These are separate DeepSeek repositories pulled in as git submodules and compiled by scripts/build_vendor.sh. They are where the raw speed comes from. Each one is a general-purpose library that happens to be tuned for V4.1.

FlashMLAvendorThe attention kernels

FlashMLA is DeepSeek's library of optimised attention kernels — the single most expensive operation in a transformer. "MLA" is Multi-head Latent Attention, DeepSeek's attention design that compresses keys and values into a small shared latent vector so the KV cache is a fraction of the usual size. This repository contains token-level sparse attention kernels for both prefill and decoding with FP8/FP4 KV caches, plus a famous fused kernel that performs Q-norm, Q-RoPE, the attention itself, the conjugate O-RoPE and the cast to FP8 all in one GPU launch, avoiding the memory round-trips that separate kernels would pay. On a B200 it reaches up to 1 460 TFLOPS in prefill and 950 TFLOPS in decoding; on the Huawei Ascend 950 the sparse kernels hit 410 TFLOPS in prefill (95% of theoretical peak) and 360 TFLOPS in decode (83%). The September 2026 release dropped support for NVIDIA Hopper and for DeepSeek V3/V3.2/V4.0 and changed the FP8/FP4 KV cache format, so it is deliberately not backward-compatible.

Why it matters here: DeepInfer's deployment Q&A admits that the public FlashMLA lacks one hand-tuned SASS (assembly) optimisation that DeepSeek's internal build has, making the public decoding kernel 5–10% slower — but end-to-end the gap is at most 5%.

DeepGEMMvendorThe matrix-multiply kernels

DeepGEMM is a unified tensor-core kernel library that collects the main computation primitives of a modern LLM into one CUDA codebase: GEMMs (matrix multiplications) in FP8, FP4 and BF16, fused mixture-of-experts with overlapped communication ("Mega MoE"), the MQA scoring kernel for the sparse "lightning indexer", and HyperConnection (HC) operators. Every kernel is compiled at runtime by DeepJIT, so installing the package needs no CUDA compilation and the kernel can be specialised to the exact shapes you use. It borrows ideas from NVIDIA's CUTLASS and CuTe but deliberately avoids their heavy template machinery, so the library stays small enough to read — DeepSeek positions it as a teaching resource for GPU optimisation as much as a production dependency. Despite the lightweight design it matches or beats expert-tuned libraries, reaching 1 550 TFLOPS on H800, and a fully API-compatible Ascend port exists as DeepGEMM-Ascend.

Mega MoE is the piece DeepInfer leans on hardest. The Q&A says it is the general solution within a scale-up domain: regardless of EP size or batch size, Mega MoE is significantly faster than an unfused MoE, because it overlaps the expert matrix multiplies with the all-to-all communication instead of doing them in sequence.

DeepEPvendorThe expert-parallel communication library

DeepEP ("DeepEveryParallel") is the communication library that makes mixture-of-experts work across many GPUs. In an MoE model each token is routed to a handful of experts, and those experts live on different GPUs, so every layer requires an all-to-all shuffle: send each token to the GPUs holding its experts (dispatch), then send the results back (combine). DeepEP provides high-throughput, low-latency GPU kernels for exactly that, including FP8 dispatch to halve the bytes on the wire, plus NVLink exchange of weights and gradients for redundant experts — which is precisely what EPLB needs when it shuffles hot experts between GPUs. V2 added a lightweight NCCL "Gin" backend, analytical SM and queue-pair sizing (no more auto-tuning), and experimental primitives for pipeline, context and data parallelism plus remote memory access for Engram. The Ascend port keeps the same buffer API and reports 313–375 GB/s dispatch across EP8–EP128 on Ascend 950DT.

DeepSelectvendorA very fast top-k

DeepSelect does one job: find the k largest values in a list, extremely fast. That sounds trivial until you realise DeepInfer does it twice per token at enormous scale — once in the sparse "lightning indexer" to pick the 512 most relevant past blocks to attend to, and once in the sampler to restrict softmax to the top few thousand of a 129 280-token vocabulary. A naïve torch.topk is memory-bound and badly tuned for these shapes, so DeepSelect specialises for exactly two cases — bfloat16 indexer workloads with topk ≤ 4 096 (optimised around topk=512), and float32 sampling over a ~128K vocabulary — and achieves 2× to 20× speedups over torch.topk. It supports both CUDA and Ascend, though only the CUDA path takes float32 input. Because top-k does no floating-point arithmetic, the library is benchmarked in effective memory bandwidth rather than FLOPS.

TileLang & TileKernelsvendorThe portable kernel language

TileLang is a domain-specific language for writing GPU kernels in Python-like syntax that compiles to multiple hardware backends — which is how DeepInfer supports both NVIDIA GPUs and Huawei NPUs without two separate hand-written kernel sets. TileKernels (installed from PyPI as tile-kernels, not a submodule) is DeepSeek's library of dozens of pre-written TileLang kernels for MoE routing, Engram gating, FP8/FP4 quantisation and manifold hyper-connection operators, most of which run near the hardware's compute or bandwidth ceiling. Separately, DeepInfer ships about 45 of its own TileLang kernels in deepinfer/model_executor/layers/tilelang_ops/, each written twice — once under cuda/ and once under asc/ — with a dispatcher that picks the backend at import time. These in-tree kernels cover the engine-specific glue: building KV indices, loading paged caches, RMSNorm, the fused sampler, and the GPU-side draft-length scheduler.

deepseek-recipesibling repoProtocol & tokenisation, open-sourced alongside

DeepInfer takes token IDs in and gives token IDs out; it knows nothing about chat formats. deepseek-recipe is the separate MIT-licensed Rust library (with Python bindings) that fills that gap: it converts Chat Completions, Responses and Anthropic Messages requests into one internal Conversation format, renders that into the exact prompt string V4/V4.1 expects, encodes it to token IDs, and parses the model's output stream back into protocol responses with reasoning content, tool calls and stop sequences. Two details are genuinely clever. First, special-token injection defence: when building the prompt it records exactly where it inserted control tokens like <|User|>, so if a user literally types that string it is encoded as ordinary text and cannot hijack the conversation. Second, segmented parallel tokenisation: because the special-token boundaries are already known, the ordinary text between them can be BPE-encoded independently and in parallel, then concatenated — which measurably cuts tokenisation latency on very long prompts. Its behaviour is aligned with the official DeepSeek API, so a third-party deployment behaves identically.

It is not a server. You still supply the HTTP transport, auth, tool execution and the inference backend. Defaults it does supply: max_tokens of 8 192 outside thinking mode, 65 536 in thinking mode, 131 072 in thinking mode at max effort.

3FS (Fire-Flyer File System)infraWhere the KV cache actually lives

3FS is DeepSeek's own distributed file system, built for AI workloads on modern SSDs and RDMA networks. It matters here because it is the storage layer underneath the production KV cache: roughly 100 PiB of SSD holding the attention keys and values of past requests so that a repeated prompt prefix never has to be prefilled twice. Data is stored with 10+2 erasure coding, meaning each group tolerates two simultaneous node failures, and a read fires requests to all 11 nodes in the group and decodes from whichever 10 respond first — latency insurance by design. A GC worker on each storage node evicts least-recently-used cache under a watermark, and DeepSeek sets a TTL of 3 days for agent traffic and 7 days for chatbot traffic (chatbot has a heavier long tail of repeat hits, and dropping to ~3 days costs it 0.5–1% of hit rate). Published 3FS cluster figures reach ~6.6 TiB/s aggregate read on 180 storage nodes.

None of this is in DeepInfer. The repo's README lists "a KV cache system" as required but not included, and the Q&A explains why: that code is tightly coupled to DeepSeek's internal infrastructure.

Model architecture (what V4.1-Flash actually is)

DeepInfer supports exactly one model, so the engine and the architecture are co-designed. These concepts explain the shapes the code keeps talking about.

MLA — Multi-head Latent AttentionmodelWhy the KV cache is small

In ordinary attention, every layer stores a full key and value vector for every token and every head; for a 128k-token context that cache becomes larger than the model weights. MLA instead projects keys and values down into a single shared low-rank "latent" vector per token, caches only that, and projects back up on demand — so the cache shrinks by roughly an order of magnitude while quality is preserved. In the code this shows up as a chain of low-rank projections: an A matrix down, an RMSNorm, then a B matrix up, with separate handling for the RoPE (rotary position) part of the key that cannot be compressed. DeepInfer fuses the up-projection of values with the output projection (_init_wv_o_proj) so the two never materialise separately. The V4.1 variant adds gating and a second compression stage on top, which is why you see kv_lora_rank, qk_rope_head_dim and compress_dim all over the cache-engine code.

MoE — Mixture of ExpertsmodelWhy a huge model is cheap to run

Instead of one giant feed-forward network per layer, an MoE layer holds hundreds of smaller "expert" networks plus a tiny gate that scores them. For each token the gate picks the top few experts (V4.1 uses 384 routed experts in the benchmark configs), so only a small fraction of the parameters do work on any given token. The model can therefore be enormous in total parameters while staying cheap per token. DeepInfer's gate uses sqrt-softplus scoring plus the noaux_tc top-k selection with a load-correction bias — and interestingly keeps two FP32 biases, one for text and one for image tokens. A "shared expert" runs for every token regardless of routing. The whole engine's decode strategy is built around the fact that the expert weights, not the activations, dominate memory traffic.

Vocabulary you'll meet in the code logical expert = one the gate can choose (n_routed_experts) · extra/redundant = a duplicate copy of a hot expert (n_redundant_experts) · physical = logical + extra, rounded up to be divisible by ep_size · local = physical ÷ ep_size, what one GPU holds.

DSA — DeepSeek Sparse Attention & the indexermodelAttending to 512 blocks, not 128 000 tokens

Full attention costs grow with the square of context length, which is unaffordable at 128k+. DSA makes attention sparse: a cheap scoring network — the "lightning indexer" — estimates how relevant each past block of tokens is to the current query, and then real attention runs only over the top few hundred blocks. The indexer is a multi-query attention (MQA) pass computing relu(q @ k) * weights logits, deliberately tiny compared to the main attention, and the selection uses DeepSelect's fast top-k. DeepInfer adds two refinements: candidate blocks, where one designated layer produces a restricted candidate set that later layers select within, and cross-layer index sharing, where consecutive layers reuse the same top-k or the same index keys instead of recomputing them. These sharing relationships are derived from the model config and validated fail-fast at startup.

SWA — Sliding Window AttentionmodelSome layers only look at the last 128 tokens

Not every layer needs to see the whole context. In V4.1 a set of layers use sliding-window attention: each query attends only to a fixed window of recent keys — 128 tokens — which makes their cost constant regardless of how long the conversation is. The engine stores that window in a ring buffer per sequence rather than in the paged block cache, since it is small, fixed-size and constantly overwritten. In the code the SWA cache lives inside a StateBlock, one fixed-size slot per sequence, and a dedicated kernel (get_kv_swa_index_decode) maps logical positions to ring slots. The interaction between SWA and prefix caching is the single trickiest part of the whole system, and is what SWA bounded replay exists to solve.

YoCo & the CED splitmodelHalf the layers don't need the full prompt

YoCo ("You Only Cache Once") splits the model into a producer half and a consumer half. The first n_prefill_layer layers compute real KV caches from the prompt; the layers after that — the "consumer" or decoder layers — derive their block KV from the last producer layer's hidden state instead of computing it themselves. In DeepSeek's CED (compress-encode-decode) architecture this means prefill only has to run the encoder layers fully, and the decoder layers' only per-layer state is their sliding window. DeepInfer exposes two truncation modes: mask keeps every query row but narrows what the SWA can see, and compact actually removes the truncated query rows so the consumer layers do less work. The two are numerically equivalent inside the retained region, and examples/yoco/yoco_equiv.py exists purely to prove that — comparing SWA pivots and visible keys cheaply (L1), or comparing logprobs element-by-element across 8 GPUs (L2).

EngrammodelA giant lookup table bolted onto the model

Engram is an external memory subsystem: alongside the normal transformer weights, the model carries enormous embedding tables indexed by n-gram hashes of the recent tokens. At certain layers the engine hashes the last N tokens, looks up the corresponding rows, projects them through a shared KV projection, and gates the result into the hidden state — effectively giving the model a vast, cheap associative memory that is read rather than computed. Because the tables are far too big for one GPU they are sharded across ranks and gathered by hash at runtime (DeepEP provides the remote-memory primitive). Engram also brings a compressed tokenizer: raw token IDs are mapped into a smaller compressed vocabulary before hashing, so the tables stay a manageable size. One independent write-up describes V4.1-Flash as a 552B backbone plus 196B Engram parameters, which gives a sense of the scale involved.

mHC — manifold HyperConnectionmodelThe residual stream, multiplied

A standard transformer has one residual stream: each sub-layer reads it, computes something, and adds the result back. mHC replaces that single stream with hc_mult parallel streams — a "trunk" of shape [tokens, hc_mult, hidden]. Before each sub-layer the trunk is mixed into that sub-layer's input with learned coefficients, and afterwards the output is mixed back into the trunk. The mixing coefficients are normalised with a Sinkhorn iteration, which keeps the mixture well-conditioned. V4.1 also uses a "shifted" variant where the mix is offset by half a layer, so each sub-layer applies the coefficients computed by the previous one and the final mix-down happens at the end of the model instead of in a separate head. DeepInfer implements this with a lazy data structure (HCLazyPostData) so the post-mix of one sub-layer and the pre-mix of the next are fused into a single kernel call.

FP8, FP4, UE8M0 — low-precision formatsmodelFour bits per weight, and the scales that make it work

Most of V4.1 does not run in 16-bit. Weights and caches are stored in 8-bit (E4M3) or 4-bit formats, with a shared scaling factor per small group of values to preserve dynamic range — this is what "per-16" or "per-32" means in the Q&A. UE8M0 is a scale format with 8 exponent bits and no mantissa, i.e. the scale is always a power of two, which makes applying it a cheap exponent add rather than a multiply; four of them pack into one int32. MXFP4 is the 4-bit format with per-32 UE8M0 scales. DeepSeek's exact production choices are documented: the main KV cache uses per-16 E4M3 (like NVFP4 but without the global scale), the indexer KV uses per-32 UE8M0 MXFP4, and the MoE routed-expert weights also use per-32 UE8M0 MXFP4. SWA KV stores 528 bytes per token — 512 bytes of FP8 data plus 16 bytes of UE8M0 scale.

Engine internals

The machinery that decides what runs, where memory goes, and how the GPU is kept busy. This is the part that is genuinely DeepInfer rather than the model.

Paged KV cache, block tables, slot mappingengineVirtual memory for attention

A sequence's KV cache grows one token at a time and you don't know how long it will get, so reserving a contiguous slab per request wastes enormous amounts of memory. The paged approach — borrowed from operating-system virtual memory — chops GPU memory into fixed-size blocks (V4.1 uses 128 tokens per block) and gives each sequence a block table: a list saying "my tokens 0–127 are in physical block 41, tokens 128–255 in block 9…". Blocks can then be allocated and freed individually with no fragmentation, and two sequences sharing a prompt prefix can point at the same physical blocks. Slot mapping is the companion idea: a flat array telling the store kernel exactly which physical slot each newly-computed token's KV should be written into. In DeepInfer the free list is a C++ intrusive doubly-linked list with reference counts, so allocate and free are O(1) and block 0 is reserved as a null/padding sentinel.

csrc/engine/block_manager.hpp
enum class AllocStatus { OK, LATER, NEVER };   // can we fit this sequence now, later, or never?

struct Blocks {  // NOTE: GPU block 0 is unused, so 0 means "empty"
    Blocks(int _n) : _blocks(_n), _head(1), _tail(_n - 1), _size(_n - 1) {
        TORCH_CHECK(_n > 1, "GPU blocks too few: ", _n);
        for (int i = 1; i < _n; ++i) { _blocks[i].prev = i - 1; _blocks[i].next = i + 1; }
        _blocks[_n - 1].next = 0;
    }
    int _pop_front() { int r = _head; _erase(_head); return r; }   // O(1) allocate
    int num_free_blocks() { return _size; }
};

The state cache & StateBlockengineThe second, separate cache

DeepInfer keeps two caches. The paged block cache holds the compressed main KV, which grows with context length. The state cache holds everything that is fixed-size per sequence: the sliding-window KV ring buffers and the compression-boundary accumulators. Each sequence gets one StateBlock slot, and that slot is deliberately partitioned into a stored region (the SWA layers that must survive across requests — the first 20 layers in V4.1) followed by a dropped region (the YoCo consumer SWA, recoverable by recomputation, plus compression state that has no cross-boundary dependency). The split exists so that persisting a sequence to disk is just "write the first state_size_to_disk bytes" — a length truncation, not a gather. The number in the Q&A: 20 layers × 134 tokens × 528 bytes = 1 415 040 bytes per sequence.

SWA bounded replayengineThe trick that makes prefix caching work with sliding windows

Here is the problem. Prefix caching lets you skip prefill when someone sends a prompt you've already seen — but only if you saved all the state, and the sliding-window KV is expensive to persist (it is per-layer and constantly rewritten). If you don't save it, a cache hit still forces you to recompute the window exactly, which for V4.1's decoder would mean pushing the last 2 560 tokens through 20 layers. Bounded replay says: don't rebuild it exactly — rebuild it approximately, by replaying only the last 128 tokens and truncating the attention window to within the replayed segment. Replaying from position s, the query at position i sees only keys in [max(s, i−127), i]. The cost becomes a constant, independent of context length and layer count. DeepSeek reports the quality loss as negligible, and the win is large: because misses are now cheap, the persistent cache can store only the global KV and skip SWA KV entirely, shrinking the stored footprint dramatically.

Two places it is used. Encoder bounded replay handles a missing SWA cache on a prefix hit. Decoder bounded replay goes further: because CED projects the decoder layers' block KV from the last encoder hidden state, each prefill only recomputes the last 128 tokens in the decoder layers and the result is used for decode only, never entering the prefix cache — which nearly halves total prefill computation.

ZOS — zero-overhead / asynchronous schedulingengineNever let the GPU wait for Python

A naïve decode step is schedule(N) → forward(N) → sample(N) → post-process(N). Two of those four stages are pure CPU work, and you need a GPU→CPU synchronisation before post-processing to learn which token was sampled. So the GPU sits idle during post-process(N) and schedule(N+1) — a bubble on every single token. Asynchronous scheduling removes it by pipelining: while the GPU runs forward(N) and sample(N), the CPU concurrently runs schedule(N+1), launches forward(N+1), post-processes step N−1, and launches sample(N+1). The GPU queue never drains. DeepSeek credits SGLang and NanoFlow for the idea and enables it by default (DEEPINFER_ZERO_OVERHEAD_SCHEDULING, on for NORMAL and COMPLETION engines).

The cost of the trick. Scheduling step N+1 before step N's result is known means the CPU's idea of each sequence's length is stale. DeepInfer fixes this on the GPU: prepare_zos_inputs builds a remap array matching this batch's rows to the previous batch's, and kernels (compute_seqlens_k_zos, gather_input_ids_zos) correct the lengths and input IDs in place. Three whole kernels exist only because of this optimisation.

CUDA graphsengineRecord the step once, replay it forever

A decode step launches thousands of tiny kernels, and at a few microseconds of CPU overhead each, the launching alone can exceed the compute. A CUDA graph captures the entire sequence of launches once and replays it as a single driver call. The catch is that a graph is frozen: fixed shapes, fixed memory addresses. There is a second, separate runner for the DFlash draft model. During startup the engine also times every captured graph to build a decode performance curve — (batch size, milliseconds) pairs — which is cached to disk and later fed to the speculative-decoding scheduler so it can predict how long a candidate batch size would take.

The scheduler: batching, chunking, preemptionengine1 329 lines of C++ deciding what runs next

Every iteration, the scheduler answers one question: what goes on the GPU this step? It maintains waiting (not started), prompted (prefilled, awaiting decode) and running queues, and a step is homogeneous — either a prefill step or a decode step, never both. Key behaviours: continuous batching, where finished sequences leave and new ones join every single iteration rather than waiting for a whole batch to complete; chunked prefill, slicing a 128k prompt into pieces so it cannot monopolise the engine (with careful logic to never cut inside an image); and preemption, where if KV blocks run out the scheduler evicts sequences — choosing victims by shortest output length (LCFS, last-come-first-served) so the most-invested requests survive. A NORMAL engine running both phases must stay in lockstep with its data-parallel peers, which it achieves by voting.

csrc/engine/scheduler.hpp — the DP voting logic
// Two kinds of attempt point:
//   ALL point (every prefill_attempt_interval = 70 decode steps):
//       only prefill if EVERY rank has prefill work — otherwise one rank works
//       while the others run an empty prompt step.
//   ANY point (every prefill_any_attempt_interval = 100 decode steps):
//       prefill if ANY rank has work — a starvation backstop for an isolated rank.
bool is_any_point = (decode_step != 0) && (decode_step % prefill_any_attempt_interval == 0);
bool is_all_point = (decode_step % prefill_attempt_interval == 0);
if (!is_any_point && !is_all_point) return _schedule_decode(acquire);

bool want = (get_gpu_cache_usage() <= GPU_CACHE_PREFILL_WATERMARK) && _has_prefill_waiting();
bool do_prefill = is_any_point
    ? (_dp_allreduce(want ? 0 : 1, ReduceOp::MIN) == 0)    // ANY
    : (_dp_allreduce(want ? 1 : 0, ReduceOp::MIN) == 1);   // ALL

// Second vote: "want" only checked that the queue was non-empty — _schedule_prefill
// can still come up empty (no slots, no KV blocks). If EVERY rank came up empty we
// must fall back to decode, or the group spins forever re-voting and re-failing.

MTP, DFlash, DSpark & the confidence headengineGuess ahead, verify in bulk

Three names for layers of the same idea. MTP (multi-token prediction) is the general technique: a small draft model proposes the next few tokens, and the big model verifies all of them in one forward pass, so a single expensive memory read can yield several accepted tokens instead of one. DFlash is DeepSeek's specific draft implementation, a lightweight head that shares the main model's KV and runs inside its own CUDA graph. DSpark is the scheduling layer on top, and it is the genuinely novel bit: a confidence head predicts the acceptance probability of each individual draft token, and the scheduler then allocates verification compute only to the tokens with the best expected return. Verification is therefore variable-length — a request whose drafts look doubtful gets fewer slots this step. Acceptance correctness is preserved by standard rejection sampling against the target distribution. Full detail and the measured gains are in section 10.

The samplerengineTurning 129 280 numbers into one token

The model outputs a score for every token in the vocabulary; the sampler picks one. In DeepInfer that is far more than a softmax. The pipeline is: gather the hidden states that need sampling → matrix-multiply against the embedding to get logits → apply the structured-output bitmask → apply temperature, top-k and top-p → sample → and, if speculation is on, verify the previous round's drafts by comparing their logprobs under the old and new distributions, accept a prefix, resample at the first rejection from the residual distribution, then run the draft head to propose the next round. A notable optimisation is force_topk: rather than softmaxing 129 280 values, restrict to the top few thousand first (default 4 096 in the offline example) and maintain an index mapping. There is also golden_token_ids for teacher-forcing, used by the evaluation and equivalence harnesses.

A small but careful detail Rejection sampling can, in theory, fail to produce any token when the residual distribution is degenerate. The kernel applies a tiny penalty alpha = exp(-5e-5) to the draft probability to guarantee progress, and tilelang_ops/common.py contains a half-page proof bounding the resulting distribution error to within (1 ± eps) of the true distribution. Batch invariance & deterministic samplingengineSame input, same output — always

Normally, running the same prompt twice on the same GPU can give different results, because floating-point addition is not associative and batching changes the order in which partial sums are reduced. Who else happened to be in your batch silently changes your logits in the last decimal places, which occasionally flips a token. For evaluation, auditing, debugging and reproducible agent runs this is maddening. Batch-invariant inference (DEEPINFER_BATCH_INVARIANT=1) forces deterministic reduction orders in the GEMM and attention kernels so results do not depend on batch composition. Deterministic sampling builds on it: with batch invariance on, variable-length MTP off (DEEPINFER_ENABLE_MTP_VARLEN=0) and a fixed seq_seed in SamplingParams, identical input tokens and parameters produce byte-identical output. Structured output (SO)engineForcing valid JSON, by construction

Structured output constrains generation so the result cannot violate a format — a regex, a JSON Schema, or an EBNF grammar. The format is compiled into a grammar automaton (DeepInfer uses xgrammar); at each decode step the automaton is advanced by the token just emitted, the set of legal next tokens is computed, and a bitmask is applied to the logits so illegal tokens get −∞ before sampling. Compilation is expensive and inference is latency-critical, so the two are decoupled: compilation runs asynchronously on a thread pool pinned to idle CPUs (in production, on a dedicated machine) and a request fetches its compiled matcher before entering the engine. DeepInfer adds two extras beyond the basics: trigger_token_ids, a token sequence that must appear before the grammar activates (so the model can think freely first), and bound_token_id, which stops free generation and forces the trigger sequence through.

Object pools & deferred releaseengineWhy the GC is switched off

At 200 decode steps per second with 60 sequences each, allocating a Python object per token per request would bury you in garbage collection pauses — and a GC pause at the wrong moment stalls the GPU. DeepInfer's answer is blunt: the worker calls gc.disable() at startup and runs a manual collection every DEEPINFER_GC_INTERVAL_STEP (default 1 000, ×10 for completion engines). Everything hot is pooled — SequenceMetadataPool, RequestOutputPool, MTPInfoPool — and the outputs handed back to Python are raw uint64 pointers into C++ storage rather than objects. Because those pointers are recycled on the next step, there is a DeferredRelease class that holds resources for exactly one extra round so the caller is guaranteed to have read them, and releases them during the next step's pre_sampler_sync — i.e. overlapped with GPU compute.

This is why llm.generate() calls RequestOutput.clone(raw_output): if you keep a RequestOutput past the current step without cloning it, you are reading recycled memory. The docstring on LLMEngine.step() says so explicitly.

Timers, profiling & MFUengineHow they know where the time goes

DeepInfer ships three timing systems. CPUTimer records wall time around named scopes. CUDATimer records GPU time with event pairs. Parallelism & infrastructure

EP, DP, CP — and why not TPparallelismFour ways to split work, three of them used

EP (expert parallelism) splits the MoE experts across GPUs; each GPU holds a slice of the experts and tokens are shuffled to wherever their experts live. DP (data parallelism) runs independent replicas, each handling different requests — in V4.1 the attention part is data-parallel with #DP = #EP. CP (context parallelism) splits a single long sequence across GPUs, which helps latency on very long prompts; DeepInfer implements a "mirror CP" variant with its own index-preparation kernels. TP (tensor parallelism), the classic approach of splitting each weight matrix, is not used in DeepSeek's production deployment at all. The Q&A's recommended settings: prefill uses EP2–8/DP2–8 (the smallest that HBM allows); decode uses EP64–128/DP64–128, the largest the GPUs allow — this is what "Wide-EP" means.

Why Wide-EP helps decode specifically Decode is memory-bandwidth-bound and the expert weights dominate the traffic. Spreading 384 experts over 64 GPUs instead of 8 means each GPU reads one-eighth as much expert weight per step, so steps get faster — provided the extra all-to-all communication (DeepEP's job) and the load imbalance (EPLB's job) don't eat the gain. The Q&A ships an EP8-vs-EP64 chart showing the difference.

Prefix caching & the three-tier KV hierarchynot shippedThe biggest cost saving of all

If a user sends a 100k-token document and asks five questions about it, prefilling it five times is pure waste. Prefix caching keeps the KV from the first pass and reuses it. DeepSeek runs a three-tier hierarchy: in-flight KV in GPU HBM; the SWA KV in local host memory with an in-memory directory sharded across entrypoint machines, so a machine that doesn't hold it can pull it over a 400G VLAN; and the persistent paged block KV on the dedicated 3FS cluster. Hiding the cost of a hit is its own engineering problem: matching is a hash-chain prefix match on metadata only but can't be hidden because the hit length determines routing; fetching from 3FS into host shared memory runs in a separate process; and swap-in from host to GPU runs in a thread, overlapping per-layer host-to-device transfers with the forward pass — using GDR/RDMA rather than the CUDA copy engine, because the copy engine performs poorly on the fine-grained block copies and RDMA saturates PCIe without consuming SMs.

Pareto curves & the metrics that mattermeasurementWhy there is no single "speed" number

Serving performance is a trade-off curve, not a number. Increase the batch size and you serve more tokens per second per GPU (good for your costs) but each individual user waits longer between tokens (bad for them). A Pareto chart plots both axes so you can pick the operating point your service level agreement allows — which is why DeepSeek published curves rather than headline numbers. The metrics: TTFT (time to first token) is dominated by prefill; TBT/TPOT (time between output tokens) is dominated by decode; throughput is tokens/s/GPU. They are not interchangeable, and comparing one project's tokens/s/user against another's tokens/s/GPU is meaningless. What a TileLang kernel actually looks like

This one computes, per row, the sum of all probabilities less than or equal to the sampled token's — an inclusive CDF used by the sampler. It shows the whole style: a JIT-decorated factory, dynamic shapes, explicit tiling and a reducer.

tilelang_ops/cuda/sum_smaller_probs.py
@tilelang.jit(out_idx=None, target="cuda", pass_configs={
        tilelang.PassConfigKey.TL_DISABLE_TMA_LOWER: True,
        tilelang.PassConfigKey.TL_DISABLE_WARP_SPECIALIZED: True})
def sum_smaller_probs_tl(vocab_size: int) -> Any:
    num_tokens      = T.dynamic("num_tokens")       # shapes resolved at call time
    logprobs_stride = T.dynamic("logprobs_stride")
    threads    = 512
    block_size = 8192 if vocab_size >= 8192 else tilelang.next_power_of_2(vocab_size)

    @T.prim_func
    def _sum_smaller_probs(logprobs, sample_results, output) -> None:
        with T.Kernel(num_tokens, threads=threads) as bx:   # one CTA per token
            T.pdl_sync()                                   # programmatic dependent launch
            thread_sum = T.alloc_reducer((1,), T.float32, replication="all")
            logprob_limit = T.alloc_var(T.float32, logprobs[bx, sample_result])
            for i0 in T.serial(n_chunks):
                T.copy(logprobs[bx, i0 * block_size], logprobs_frag)   # global → fragment
                for j in T.Parallel(block_size):
                    if val < logprob_limit or (val == logprob_limit and col <= sample_result):
                        thread_sum[0] += T.exp(val)
            T.finalize_reducer(thread_sum)
    return _sum_smaller_probs

Decisions worth stealing

Decode writes to disk even though it never reads from it

KV offload is off during decode — decode isn't capacity-bound, so there's nothing to gain. But the KV produced during decode is still written out, purely to raise the hit rate for the next conversation turn.

Store SWA only on 128-token boundaries

After prefill, reserve one token at the end and round down to a multiple of 128; if that leaves less than a full unit, store nothing. During decode, a replica region on-device is copied each time a request crosses a boundary. Overshoot by at most 5 tokens is absorbed by 6 extra ring-buffer positions.

No TTL logic in the cache store at all

Reclamation is entirely 3FS's own garbage collection — one GC worker per storage node, evicting LRU under a disk watermark. Fewer moving parts, and the file system already has to solve it.

Shorter TTL has a measurable price

Chatbot traffic has a heavy long tail — a small amount of KV read very many times. Dropping from 7 days to ~3 costs 0.5–1% of overall cache hit rate. That is the kind of number you only get from running the thing at scale.

10 Speculative decoding & DSpark

The one place where DeepInfer does something genuinely new rather than doing a known thing very well.

The base idea

Decode is memory-bound: reading the model's weights to produce one token costs almost the same as reading them to produce six. So have a cheap draft model propose the next few tokens, then run the big model once over all of them and check which it agrees with. Accepted drafts are free tokens. Rejection sampling at the first disagreement guarantees the output distribution is unchanged — this is mathematically exact, not an approximation.

The scheduler's actual search

This is the core of mtp_varlen.hpp: sort every draft token across every request by predicted acceptance, then walk the list adding one token at a time and ask "does this batch size still improve throughput?"

csrc/engine/mtp_varlen.hpp — MTPVarlen::schedule (condensed)
// Sort all (acceptance_rate, seq_idx) pairs descending
std::sort(acc_queue_for_bsz.begin(), acc_queue_for_bsz.end(), by_rate_desc);

double best_throughput = 0.0;  int best_bsz = 0;
float cur_expected = num_seqs;    // the guaranteed tokens (one per sequence)
int   cur_bsz      = num_seqs;

auto update_best = [&]() {
    const auto &[graph_size, baseline_ms] = _decode_perf_curve[cur_bsz_idx];
    // predicted step time = profiled CUDA-graph baseline
    //                     + fitted per-token slope (context-length effect)
    //                     + measured sampler time (median of recent steps)
    const double time_ms = baseline_ms + slope_ms * graph_size + sampler_ms;
    const double cur_throughput = cur_expected / time_ms;
    if (cur_throughput > best_throughput) { best_throughput = cur_throughput; best_bsz = cur_bsz; }
};

update_best();                            // batch of just the golden tokens
for (auto &acc : acc_queue_for_bsz) {   // then add drafts, best-first
    cur_expected += acc.first;           // expected extra accepted tokens
    cur_bsz      += 1;                  // definite extra compute
    update_best();
}

// Hand out best_bsz - num_seqs slots to the highest-confidence drafts
seqlens_q.assign(num_seqs, 1);
for (int i = 0; i < best_bsz - num_seqs; ++i) seqlens_q[acc_queue_for_seqs_q[i].second] += 1;
The timing model is self-tuning _decode_perf_curve is the startup CUDA-graph profile. On top of it, ForwardRuntimeEstimator fits a per-token slope (context length affects step time, which the static curve ignores) and SamplerRuntimeEstimator tracks a rolling median of sampler time — both using median-of-medians so one slow step doesn't poison the estimate. The scheduler is therefore continuously re-calibrating against the machine it is actually running on.
The round-counting subtlety Under async scheduling the confidence from step N hasn't come back when step N+1 is scheduled. So the code tracks schedule_cnt and process_cnt per sequence; they can differ by at most one, and that tells it whether the stored accept_rates are from round N−1 or N−2. It deliberately uses the older round to pick the total batch size (so that confidence for draft i+1 can never influence whether draft i is verified) and the newer one to distribute slots. That is a careful piece of reasoning hiding in a 30-line comment.

Chunked prefill, and the cost model behind it

A 128k-token prompt processed in one step would block every other user for hundreds of milliseconds. Chunked prefill slices it. The open-source scheduler uses a token budget (max_num_batched_tokens); the production prefill balancer goes further and solves for the chunk size:

Each prefill step gets a time budget compute_quota_limit in nanoseconds. A fitted quadratic cost model cost(q, c) predicts the step duration from q (new tokens) and c (prefix already computed). The scheduler solves that quadratic for the largest q that stays under 32 768 tokens while exactly consuming the remaining budget — then the budget itself is reduced by an all-reduce MIN across the DP group, so no rank runs long and strands the others.

The determinism recipe

Three settings, all required together, NVIDIA only:

Batch invariance alone

Gives you identical logits regardless of who shares your batch. Sampling is still random.

+ fixed seq_seed

Gives you identical tokens. The sampling kernel is deterministic in (seed, position), independent of batch size and row order.

+ MTP varlen off

Needed because variable-length verification changes how many rows are in flight, which changes reduction shapes.

Where the preemption policy bites

When KV blocks run out mid-decode, something has to give. DeepInfer sorts running by output length and preempts from the shortest end — last-come-first-served — so the requests that have already consumed the most compute are protected. Preempted sequences either return to the queue or, with stop_preempted_request=True (the default outside the offline LLM wrapper), are terminated.

With YoCo truncation enabled, the code explicitly notes that preemption is allowed to change results — because the replayed suffix after a restart may differ. If you need bit-exact reproducibility, you need headroom so preemption never happens.

Reading any of these numbers responsibly

Not a comparison with other engines

There is no published head-to-head against vLLM or SGLang on the same hardware and workload. Each project benchmarks its own setup.

Not Ascend data

Both charts are SM100. Ascend 950 is a supported target with no published throughput at all — you'd have to validate it yourself.

Not a cost model

Tokens/s/GPU is not dollars per million tokens until you add utilisation, power, depreciation, networking, storage and failure overhead.

Not TTFT

Prefill latency here is per step, not time to first token. Decode per-user speed is steady-state, not single-call latency. Network, queueing and tokenisation are all excluded.

Offline ≠ online

The Q&A says production load balancing reaches about 80% of a perfectly balanced offline benchmark. These curves are an upper bound.

The profiler lies

The examples README warns step times inside a trace include profiler overhead (up to ~50% inflation at batch 1) and that a residual 7–11% slowdown persists after the profiler exits. Sweeps therefore run with PROFILE=0.

The production claim, separately One cluster serving 155 trillion tokens per day at US$38 revenue per GPU-hour (valley pricing). That is a scale statement, not a benchmark: no cluster size, GPU mix or measurement window is given, and revenue is not profit, so it cannot be converted into a cost per token.

15 The production Q&A, distilled

doc/inference_deployment_qa.md is 312 lines and is, for my money, the most valuable file in the repository — a working description of how a frontier inference service is actually run. Here is all of it, compressed.

QuestionAnswer
What shape is the system?Disaggregated E/P/D — vision encoder, prefill and decode pools — plus dedicated storage nodes.
Parallelism?Prefill EP2–8/DP2–8 (smallest HBM allows). Decode EP64–128/DP64–128 (largest GPUs allow). VE: one GPU per instance, cheaper GPUs fine. TP and CP unused.
Why Wide-EP for decode?It substantially reduces per-step memory traffic in the MoE part and, with good EPLB, raises TPS. An EP8-vs-EP64 chart is included.
Minimum deployment?1P + 1D is deployable. P:D GPU ratio is ~1:1 in practice, and decode wants EP64+, so the smallest efficient unit is 64 + 64 GPUs.
Across data centres?Technically feasible because V4.1 compresses KV so heavily. Budget ~400 Gbps per 8 GPUs. Reliability cost is real — inter-DC fibre gets cut by construction work. DeepSeek uses adjacent DCs.
Storage server spec?20 × 30.73 TB SSDs per server, ≥40 GB/s read and ≥5 GB/s write, enough capacity for 24 h of data. Scale server count with deployment size.
Storage-to-GPU ratio?~14.4 TB logical per GPU; physical requirement is higher.
3FS properties?10+2 erasure coding, tolerates 2 node failures per group. A read fans out to all 11 nodes and decodes from the first 10 replies. One GC worker per storage node evicts LRU under a watermark.
Prefill EPLB?Start 4 redundant experts/GPU, 100-step window, reassign every 1 000 steps. Measured moe_lb 1.074 (EP4DP4) / 1.045 (EP2DP2).
Decode EPLB?Start 1 redundant expert/GPU (7/GPU after rounding at EP64, excluding the shared expert), 1 000-step window, reassign every 10 000 steps. moe_lb 1.090.
Prefill load balancer?Four context-length tiers; engines per tier redistributed by last round's demand; engines pull by remaining quota; within a GPU, FIFO with a chunk size solved from a quadratic cost model against a per-step nanosecond budget, all-reduce MIN across the DP group.
Decode load balancer?Uniform across all decode GPUs, balancing request count and total KV length simultaneously: short requests to low-concurrency/long-KV GPUs, long requests to short-KV GPUs.
Vision encoder balancer?Machine-granularity random pick, then the GPU currently processing the fewest patches — computed directly as (w/patch) × (h/patch).
How much does LB buy?Roughly 80% of a perfectly balanced offline benchmark.
KV offload during decode?No — decode isn't capacity-bound, so Hi-Sparse isn't used either. Decode KV is still written to disk to raise the future hit rate.
Expiry / TTL?No TTL logic in the cache store; 3FS GC handles it. ~100 PiB SSD, 3-day TTL for agent traffic, 7-day for chatbot. Dropping chatbot to ~3 days costs 0.5–1% hit rate.
Hiding cache overhead?Matching: metadata-only hash-chain prefix match at the entrypoint — can't be hidden, since hit length determines routing. Fetch: async, separate process, 3FS → host shared memory. Swap-in: in-engine thread, per-layer H2D overlapped with forward, implemented with GDR because the CUDA copy engine handles fine-grained block copies poorly.
Autoscaling?Prefill sizes from non-cached token count, decode from running-request count; both rate-limited and bounded. A decode engine given a shutdown notice takes a 1-minute grace period and forwards unfinished requests plus their KV to other engines in one shot.
Redundant quota?Ready machines held in a pool, plus more instances online than computed demand. Scale-in forbidden above 0.8 quota utilisation.
EP failover?One dead GPU kills the instance (single communication domain). On restart the platform re-derives EP size from the healthy GPUs, and the instance adopts whatever count it receives.
Where is FP4 used?Main KV: per-16 E4M3 (NVFP4 without the global scale). Indexer KV: per-32 UE8M0 MXFP4. MoE routed-expert weights: per-32 UE8M0 MXFP4.
Mega MoE?The general solution inside a scale-up domain — significantly faster than unfused MoE regardless of EP size or batch size.
Better internal kernels?Broadly the same. Indexer and mega series differ somewhat. Public FlashMLA lacks one hand-tuned SASS optimisation → decode kernel 5–10% slower. End to end: at most 5% apart.
Speculative decoding gain?Dynamic-length verification cuts verified drafts per step ~30% (5.00 → 3.2–4.4) with essentially unchanged accepted length (3.29 → 3.20). +4–7% throughput at the ~60 seqs/rank production point.
Structured output workflow?Compilation decoupled from inference: a dedicated SO machine compiles the constraint into a grammar automaton; at each decode step the automaton advances, legal tokens are computed, and a mask is applied to the sampling logic.

16 What's missing

Stated plainly by DeepSeek in the README, and expanded on by independent write-ups. If you are planning anything with this, read this section twice.

1 · No KV cache system

You get the in-GPU paged cache and the hooks to store and load state. You do not get: prefix matching, a metadata service, a distributed store, eviction and TTL, cross-machine transfer, fault tolerance, or cache-aware routing. One write-up calls this "a storage team's worth of work", which sounds about right.

2 · No P/D disaggregation

The engine types exist and the README says most engine functionality is implemented. The orchestration is not: KV handoff between pools, a directory of cache locations, and routing that weighs both cache placement and decode occupancy.

3 · No load balancing

All four production balancers are documented and none is shipped. EPLB — the intra-instance one — is included; the inter-instance ones are not. A round-robin router will not reach the published 80%-of-ideal figure.

18 Glossary

Every abbreviation, in one place. Filter it with the search box at the top of the page.

TermMeaning
Batch invarianceA guarantee that a request's output does not depend on which other requests shared its batch. Needed because floating-point reductions change with batch shape. DEEPINFER_BATCH_INVARIANT=1, NVIDIA only.
Block tablePer-sequence list mapping logical token ranges to physical KV cache blocks — the page table of the paged cache.
CACompressed/context attention — the dense-but-compressed attention path, as opposed to the sliding-window and sparse-indexed paths.
Candidate blocksA restricted set of KV blocks produced by one designated layer, within which later layers select their top-k. Saves repeated scoring over the whole context.
CANNHuawei's Compute Architecture for Neural Networks — the Ascend equivalent of CUDA. DeepInfer requires 9.2.
CEDCompress-Encode-Decode: V4.1's layer structure where decoder layers derive their KV from the last encoder layer's hidden state rather than computing it. Enables decoder SWA bounded replay.
Chunked prefillSplitting a long prompt's prefill across several steps so it cannot monopolise the engine.
Continuous batchingAdding and removing sequences from the running batch every iteration, instead of running fixed batches to completion.
CPContext parallelism — splitting a single sequence across GPUs. DeepInfer implements a "mirror CP" variant. Not used in DeepSeek production.
CUDA graphA recorded sequence of kernel launches replayed as one call, removing per-kernel CPU launch overhead.
DeepEPDeepSeek's expert-parallel communication library: MoE all-to-all dispatch/combine, FP8 dispatch, NVLink expert-weight exchange.
DeepGEMMDeepSeek's matrix-multiply kernel library: FP8/FP4/BF16 GEMM, Mega MoE, MQA indexer scoring, HC operators, JIT-compiled.
DeepJITThe runtime kernel compiler used by DeepGEMM and DeepEP, so installation requires no CUDA compilation.
DeepSelectDeepSeek's specialised top-k kernel, 2–20× faster than torch.topk for the indexer and sampler shapes.
DFlashDeepSeek's draft-model implementation for speculative decoding, with its own CUDA graph runner and a confidence head.
DPData parallelism — independent replicas handling different requests. In V4.1, attention is data-parallel with #DP = #EP.
DSADeepSeek Sparse Attention — attending only to the top-scoring blocks chosen by a lightweight indexer, instead of the full context.
DSparkThe confidence-scheduled, variable-length verification layer on top of speculative decoding. The novel part.
E4M3 / E2M1FP8 and FP4 formats named for their exponent and mantissa bit counts.
EngramAn external n-gram memory: huge hash-indexed embedding tables, sharded across ranks, gathered and gated into the hidden state.
EPExpert parallelism — splitting MoE experts across GPUs so each holds a slice.
EPLBExpert-Parallel Load Balancing — redundant copies of hot experts plus periodic re-placement, measured by moe_lb.
EPDEncoder / Prefill / Decode disaggregation — running the three phases on separate pools of machines.
FlashMLADeepSeek's attention kernel library: sparse prefill and decode with FP8/FP4 KV, plus the fused norm→RoPE→attn→RoPE→cast kernel.
FTPFirst token position — the index of a request's first packed row in a flattened batch. A negative value marks CUDA-graph padding.
GDRGPUDirect RDMA — moving data into GPU memory over the network without consuming SMs, used for KV swap-in because the CUDA copy engine handles fine-grained block copies poorly.
Golden tokensForced token IDs for teacher-forcing, used by the evaluation and YoCo equivalence harnesses.
HC / mHC(manifold) HyperConnection — replacing the single residual stream with hc_mult parallel ones, mixed with Sinkhorn-normalised coefficients.
LCFSLast-come-first-served — the preemption order; the shortest-output sequences are evicted first so the most-invested requests survive.
Mega MoEDeepGEMM's fused MoE path with overlapped communication. The general choice inside a scale-up domain.
MFUModel FLOPs Utilisation — achieved FLOPs over hardware peak. DeepInfer's estimator deliberately excludes draft-model FLOPs.
MLAMulti-head Latent Attention — compressing K and V into a shared low-rank latent so the KV cache shrinks dramatically.
moe_lbThe MoE load-balance statistic: slowest rank's load ÷ mean. 1.0 is perfect; production sees 1.045–1.090.
MQAMulti-Query Attention — many query heads sharing one key/value head. Used by the lightning indexer because it is cheap.
MTPMulti-Token Prediction — predicting several future tokens at once; the basis of speculative decoding here. Depth set by DEEPINFER_USE_NEXTN_DECODE.
MXFP44-bit floating point with per-32 UE8M0 scales. Used for indexer KV and MoE routed-expert weights.
nextnShorthand for the speculative draft depth. Default 5; the published decode chart uses 3.
Paged KV cacheStoring attention KV in fixed-size blocks with a per-sequence block table, eliminating fragmentation and enabling prefix sharing.
Pass@1Accuracy of a single sampled attempt, averaged over samples and tasks. The eval harness's headline metric.
PDLProgrammatic Dependent Launch — a CUDA feature letting a kernel begin setup before its predecessor fully drains. Enabled for DeepGEMM and TileKernels.
Prefill / DecodeThe two phases: reading the prompt (compute-bound, parallel) and generating tokens (bandwidth-bound, serial).
PreemptionEvicting a running sequence when KV blocks run out, freeing its memory.
RoPE / YaRNRotary position embedding, and the YaRN interpolation scheme that extends it to longer contexts than training used.
SASSNVIDIA's native GPU assembly. The Q&A notes public FlashMLA lacks one hand-tuned SASS optimisation.
Slot mappingA flat array telling the store kernel the physical cache slot for each newly-computed token.
SM100NVIDIA's Blackwell-generation streaming multiprocessor architecture — the only supported NVIDIA target.
SOStructured Output — constraining generation to a regex, JSON Schema or EBNF grammar via a per-step token bitmask.
State cache / StateBlockThe second cache: one fixed-size slot per sequence holding SWA ring buffers and compression accumulators, split into stored and dropped regions.
SWASliding Window Attention — attending only to a fixed window of recent tokens (128 in V4.1), making those layers' cost constant.
SWA bounded replayRebuilding a missing sliding-window cache by replaying only the last 128 tokens with a truncated window, at constant cost.
Symmetric memoryMemory mapped at matching addresses across ranks, letting a GPU read a peer's buffer directly. Used to shuffle expert weights within a node.
TBT / TPOTTime Between Tokens / Time Per Output Token — the decode latency metric users feel.
TileLangA multi-backend DSL for GPU kernels. How DeepInfer supports NVIDIA and Ascend from (mostly) one source style.
TMATensor Memory Accelerator — NVIDIA's async bulk-copy engine. Scale-factor layouts are TMA-aligned to use it.
TPTensor parallelism — splitting individual weight matrices across GPUs. Notably not used in DeepSeek production.
TTFTTime To First Token — the prefill-dominated latency metric.
UE8M0A scale format with 8 exponent bits and no mantissa — scales are powers of two, so applying one is an exponent add. Four pack into an int32.
UserbufferProcess-wide symmetric communication buffers used for EP all-to-all, CP all-gather and expert shuffling.
Wide-EPExpert parallelism at 64–128 GPUs, the decode configuration. Cuts per-GPU expert memory traffic at the cost of communication and a larger failure domain.
xgrammarThe grammar-automaton library behind structured output. Pinned at 0.2.2.
YoCo"You Only Cache Once" — the producer/consumer layer split plus its prefill truncation modes (mask / compact).
ZOSZero-Overhead Scheduling — overlapping CPU scheduling and post-processing with GPU execution so the GPU never idles.
3FSFire-Flyer File System — DeepSeek's distributed file system; the storage layer under the production KV cache.
